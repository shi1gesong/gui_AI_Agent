项目：基于多模态大模型的桌面GUI智能体开发与优化
第4周：端到端 GUI 智能体 v1.0 | 2026年11月24日

## 一、本周任务目标

按项目周计划，第4周要把前三周的感知、控制与 Agent 模块集成为完整闭环：“用户指令 → 屏幕感知 → 任务规划 → 动作执行 → 结果反馈”，提供简单的命令行交互界面，并测试调试 5 个基础桌面任务：打开浏览器、搜索指定内容、打开指定文件、发送消息、关闭应用。

## 二、第3周遗留问题与本周对策

| 第3周遗留问题 | 第4周对策 |
|---|---|
| Acting 只输出目标文字，没有“文字 → 坐标”的 grounding | `agent/grounding.py`：在 OCR 结果中模糊匹配目标文字（容忍空格、标点、全半角、个别错字），取 bbox 中心点 |
| 动作空间只有 click/type/scroll/key，无法打开程序、按组合键、等待 | 扩展为 10 种：新增 open_app、close_app、hotkey、double_click、wait、done |
| DPI 缩放 ≠ 100% 时，截图像素与鼠标坐标不一致 | `perception/screen_parser.py` 每次感知都计算 截图尺寸 / 鼠标坐标系尺寸，把 OCR 坐标换算成鼠标坐标 |
| Agent 从不真正执行动作，Reflect 却判定完成 | 闭环中每步真实执行并记录结果；成功 = 全部执行成功 + Reflect 完成 + **客观检查器通过** |
| qwen3:8b 的规划每次写法不同，Acting 跟着不稳定 | 规则模板 + LLM 混合规划：5 个基础任务走模板，模板识别不了的指令交给 LLM |

## 三、系统设计

### 3.1 闭环流程

```
用户指令
  │
  ▼
HybridPlanner ── 规则模板匹配？──是──► 标准子任务（每条都能被规则唯一解析）
  │否                                    │
  └──► LLM 规划（qwen3:8b）──────────────┤
                                         ▼
                          ┌──── 逐个子任务 ────┐
                          │ 需要看屏幕吗？        │
                          │  否：规则动作          │  open_app / hotkey / wait / 输入到当前焦点 …
                          │  是：截图 → OCR → DPI 换算 → 元素列表
                          │      规则能推断 → 规则动作；否则 → LLM 决策（校验 + 带原因重试 + 兜底）
                          │ 执行：grounding（文字→坐标）→ pyautogui / AppManager
                          │ 失败：等待 → 重新截图 → 重新决策（默认重试 1 次）
                          └─────────────────────┘
                                         ▼
                Reflect（LLM 判断 + 规则把关）→ 检查器（基础任务）→ trace.json + 每步截图
```

### 3.2 新增 / 修改的模块

| 模块 | 作用 |
|---|---|
| `agent/gui_agent.py` | 闭环主循环 GUIAgent：规划、逐步感知-决策-执行、失败重试、反思、检查器、轨迹记录 |
| `agent/planner.py` | RulePlanner（5 个基础任务 + 通用打开/关闭程序，支持“然后”串联）+ HybridPlanner（auto/rule/llm 三种模式） |
| `agent/grounding.py` | 文本 → OCR 元素 → 坐标，模糊匹配与排序 |
| `perception/screen_parser.py` | 感知管线：截图 → OCR → 置信度过滤 → 去重 → 阅读顺序排序 → DPI 坐标换算 → 给 LLM 的屏幕描述 |
| `control/app_manager.py` | 程序启动（内置程序表 / 默认程序打开文件 / Win 搜索退路）、按标题关闭窗口、等待窗口出现 |
| `agent/executor.py` | 新增 6 种动作的执行；记录点击坐标与匹配分数；DryRunExecutor 只决策不执行 |
| `agent/action_validator.py` | 新动作的意图识别、校验与规则兜底 |
| `agent/llm_interface.py` | Ollama 新增 think（关闭 qwen3 思考模式以加速）、temperature 参数 |
| `agent/cli.py` | 命令行：单条指令、交互模式、`--plan-only`、`--dry-run`、`--task T1~T5` |
| `agent/basic_tasks.py` | 5 个基础任务的定义、检查器、批量运行与结果统计（CSV + Markdown） |
| `apps/mock_chat.py` | 模拟聊天程序，“发送消息”任务的测试目标 |

### 3.3 三种决策模式

| 模式 | 说明 | 适用 |
|---|---|---|
| hybrid（默认） | 规则能从子任务推断出动作就用规则，推断不出才调用 LLM | 日常使用；5 个基础任务不调用 LLM 也能完成 |
| llm | 每个子任务都让 LLM 决策（仍有校验、重试、兜底） | 对比实验：衡量模型本身的决策能力 |
| rule | 完全不用 LLM | Ollama 未启动时 |

选择 hybrid 作为默认的原因：qwen3:8b 每次调用要数秒，且第2-3周真机实测语义准确率约 91%（20/22）；基础任务的步骤是确定的，用规则更快更稳，LLM 留给规则覆盖不到的开放指令。这个选择意味着 5 个基础任务的成功率主要反映的是**感知、grounding、执行链路**的可靠性，模型能力需要用 `--act llm` 单独测量（第五节）。

### 3.4 命令行用法

```bat
python -m agent.cli "在浏览器中搜索天气预报"
python -m agent.cli --plan-only "给张三发送消息：今晚7点开会"
python -m agent.cli --dry-run "关闭计算器"
python -m agent.cli --task T4
python -m agent.cli                 :: 交互模式，输入 q 退出
```

每次运行在 `runs\<时间>\` 下保存 `trace.json`（规划来源、每步动作、决策来源、点击坐标、OCR 元素数、耗时、反思结果）和每次感知的截图，方便调试。紧急停止：把鼠标甩到屏幕任意一角（pyautogui FAILSAFE），或按 Ctrl+C。

## 五、问题排查记录

| 问题现象 | 原因 | 解决方案 |
|---|---|---|
| 子任务“在‘消息内容’框中输入‘今晚开会’”输入了“消息内容” | 输入内容取的是第一个引号 | 只取“输入”之后的引号；输入框名单独解析 |
| 模拟桌面上 T4 的消息没有输进输入框 | 混合模式先用空屏幕推断动作，没找到输入框时被判成“无需看屏幕” | 保留输入框名，先截图识别输入框并点击，再输入 |
| 窗口刚打开、联系人还没画出来时点击失败且不重试 | 规则把“目标暂时不在屏幕上”当成“无法推断” | 区分两种情况，前者等待后重新截图重试 |
| 打开路径含 edge/calc 等字样的文件时，可能被当成浏览器/计算器 | 程序名模糊匹配作用在了文件路径上 | 先判断是否像路径；是路径就按文件处理 |
| 真机 T4：每步都成功但消息没发出去，输入目标是命令行里打印的整句子任务 | 全屏 OCR 读到了 Agent 自己在命令行打印的日志；占位文字没精确识别时，“包含即匹配”选中了命令行那一整行 | 感知只看前台窗口并排除命令行窗口；长句中含目标的不算匹配；校验与执行统一打分 |
| 真机 T4 第二轮：不再输进命令行，但仍 0/3 | EasyOCR 识别不出输入框里的灰色占位文字；找不到输入框时执行器“输入到当前焦点”还报成功 | 找不到输入框时如实报错；模拟聊天加可识别的“消息内容”标签、选中联系人后自动聚焦输入框 |
| 关闭应用时可能误关用户其他窗口 | — | 只关闭标题匹配的窗口，发送 WM_CLOSE（等同点 ×），不强杀进程；有未保存内容时程序会弹窗而不是丢数据，此时判为失败 |
| qwen3:8b 每步耗时长 | 默认开启思考模式 | CLI 默认 `think=false`、`temperature=0`；可用 `--think` 打开 |

## 六、已知局限

1. 修复后的真机第二轮（5 个任务各 3 次）以及 qwen3:8b 在新动作空间上的表现，还需要在 Windows 本机运行。
2. T2 搜索依赖浏览器窗口标题包含搜索词来判定；如果默认搜索引擎的结果页标题不含搜索词，检查器会误判失败。
3. 规则模板覆盖面有限，换一种说法（例如“帮我上网查查天气”）会交给 LLM 规划，效果取决于模型。
4. 只用 OCR 文字定位，没有文字的图标按钮（如浏览器的刷新图标）目前点不到，需要第5周引入视觉模型或控件树。
5. 感知用 CPU 跑 EasyOCR，云端 1920×1080 全屏每次约 4~6 秒，2560×1440 预计更慢，是端到端耗时的主要来源。

## 七、下周计划（第5周）

1. 根据真机结果修复问题，统计 5 个任务各 3 次的成功率。
2. 对比 hybrid 与 llm 两种决策模式的成功率与耗时，作为模型优化的基线。
3. 引入 UI Automation 控件树或多模态模型，解决无文字图标的定位问题。
4. OCR 只识别前台窗口区域，减少识别耗时。
