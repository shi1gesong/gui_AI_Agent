## 二、测试对象与设计

### 2.1 5 个基础任务

| 编号 | 任务 | 指令（CLI 中可直接输入） | 规划出的子任务 | 客观检查器 |
|---|---|---|---|---|
| T1 | 打开浏览器 | 打开浏览器 | 打开浏览器 → 等待2秒 | 前台窗口标题含 Edge/Chrome/Firefox/必应 |
| T2 | 搜索指定内容 | 在浏览器中搜索天气预报 | 打开浏览器 → 等待 → 按 ctrl+l → 直接输入“天气预报”并按回车 → 等待 | 有浏览器窗口标题包含“天气预报”（搜索结果页标题） |
| T3 | 打开指定文件 | 打开文件 %TEMP%\gui_agent_week4\gui_agent_week4_demo.txt | 打开文件“路径” → 等待 | 出现标题含该文件名的窗口（测试前自动生成文件） |
| T4 | 发送消息 | 给张三发送消息：今晚7点开会 | 打开模拟聊天 → 等待 → 点击联系人“张三” → 在“消息内容”框中输入“今晚7点开会” → 点击“发送” → 等待 | 模拟聊天程序的日志里有发给“张三”、内容为“今晚7点开会”的记录 |
| T5 | 关闭应用 | 关闭计算器 | 关闭计算器 → 等待 | 测试前打开计算器，任务后不再有“计算器/Calculator”窗口 |

**为什么“发送消息”用模拟聊天程序**：给真实联系人发消息是对外的、不能撤回的操作，反复测试时不合适；真实聊天软件界面随版本变化，也不利于对比实验。`apps/mock_chat.py` 的界面元素与常见聊天软件一致（联系人列表、当前聊天对象、输入框、发送按钮），全部是可被 OCR 识别的中文文字，并把每次发送写入日志供检查器判定。规划器同样支持“用微信给张三发消息：…”，但默认不在测试中使用。

**T4 是唯一必须“看屏幕”的任务**：要点击“张三”“发送”，必须先截图、OCR 识别出文字和位置，再换算成鼠标坐标（文本 → OCR bbox → 坐标，即第3周缺失的 grounding）。T1/T2/T3/T5 的每一步（打开程序、组合键、输入到当前焦点、关闭窗口、等待）都不需要截图，`hybrid` 模式下会跳过感知，节省 OCR 时间。

## 四、开发中由测试发现并修复的问题

| # | 现象 | 发现它的用例 | 原因与修复 |
|---|---|---|---|
| 1 | “在‘消息内容’框中输入‘今晚开会’”被解析成输入“消息内容” | test_action_space | 第3周规则取第一个引号作为输入内容；改为只取“输入”二字之后的引号 |
| 2 | 模拟桌面 T4 失败：消息内容输入到了“空气”里 | test_gui_agent（T4 rule） | 混合模式先用空屏幕推断动作，找不到输入框时 target 为空，被当成“无需看屏幕”直接输入；改为保留输入框名，触发截图后再点击输入框 |
| 3 | “给张三发送消息”（没有内容）被解析成发送“消息”二字 | test_planner | 正则把“消息”吞进了内容；增加无内容判断 |
| 4 | 子任务超过 max_steps 被截断时仍判定“全部执行” | test_gui_agent | 改为与规划的子任务总数比较 |
| 5 | 聊天窗口还没加载出联系人时，规则直接放弃、不再重试 | test_gui_agent（重试用例） | 区分“规则推断不出”（不重试）和“目标暂时不在屏幕上”（等待后重新截图重试） |
| 6 | “关闭当前窗口”解析成关闭“当前” | test_action_space | 修正后缀处理顺序 |
| 7 | OCR 结果“设置…”与“设置”匹配不上 | test_grounding | NFKC 归一化把“…”变成“...”，标点表补上半角句点 |
| 8 | **真机 T4（第一轮）**：每步都显示成功，但聊天记录为空；第 4 步的输入目标变成了「4。在"消息内容"框中输入 "今晚7点开会"」 | Windows 真机 test_real_T4_send_message | 全屏 OCR 也识别到了 Anaconda Prompt 里 Agent 自己打印的子任务文字。占位文字“消息内容”没被精确识别出来时，旧的“包含即匹配”规则选中了命令行里含“消息内容”的那一整行，于是点击了命令行、消息输进了命令行。修复三处：① 感知只保留前台窗口内的文字，并始终排除命令行/终端窗口；② 目标只是长句中的几个字（长度比 < 0.4）时不算匹配，校验兜底与执行器统一使用同一套打分（OCR 错字“消息内客”仍能匹配）；③ 模拟聊天占位文字颜色加深，便于 OCR。模拟桌面加入命令行窗口与 OCR 错字复现了该问题（去掉修复②时回归用例失败），修复后通过 |
| 9 | **真机 T4（第二轮）**：0/3，每步 ✓ 但聊天记录为空 | Windows 真机 test_real_mock_chat_ocr_recognizes_widgets、basic_tasks | EasyOCR 识别不出输入框里的灰色占位文字；找不到输入框时执行器把文字“输入到当前焦点”并报成功。修复：① 执行器在指定的输入框找不到时**如实报错**（会重新截图重试，仍找不到则任务失败），不再假装成功；② 模拟聊天在输入框左侧加黑色“消息内容”标签（点击标签即聚焦输入框），并且选中联系人后输入框自动获得焦点（与常见聊天软件一致）；③ 浏览器“地址栏”不可见时改用 ctrl+l 聚焦后输入。模拟桌面新增“输入框文字没识别出来”的回归用例；云端真实 EasyOCR 端到端重新通过 |
| 10 | **真机纯 LLM 决策 T2 搜索 0/3**：每步执行成功、检查器也通过，任务却判为失败 | Windows 真机 `basic_tasks --act llm` | qwen3:8b 反思时以“用户尚未查看天气预报结果”判未完成，追加了指令没要求的步骤（反思过严）。修复：① Reflect 提示词写明“只看任务目标要求的操作，不追加没要求的事情”；② 规则把关：全部子任务真实执行成功、且 LLM 的理由只是要求“查看/阅读/浏览结果”时改判完成，原判断保留在轨迹的 `llm_is_complete` 与 `override_reason` 中；有子任务失败、或指令本身就要求查看时不改判。新增 7 个用例 |
| 11 | **真机纯 LLM 决策 T2**：子任务“直接输入“天气预报”并按回车”，LLM 输出的 type 动作带了 target_text「天气预报」且漏了回车 | Windows 真机 `basic_tasks --act llm` 轨迹 | 执行器会先点击屏幕上的“天气预报”字样再输入，可能抢走地址栏焦点；这次能成功，多半是点中了地址栏下拉里的历史搜索项，属于碰巧。修复：校验通过后用 `normalize_action` 补齐细节，“直接输入”时清空 target_text，子任务要求按键而动作里没有时补上 follow_up。动作类型不变。新增 7 个用例 |

#### 对比分析

**hybrid + qwen3:8b（15/15）**
- 5 个任务的规划都命中了规则模板，逐步决策也都由规则完成，LLM 决策步数为 0。
- LLM 只在最后做了一次 Reflect，每个任务因此多出约 2.5 秒。
- 15 次 Reflect 的结论都和检查器一致。

**纯 LLM 决策（修复前 12/15 → 修复后 15/15）**
- 失败全部来自 T2。3 次运行里每一步都执行成功，检查器也判定“浏览器窗口包含搜索词”，但 qwen3:8b 的反思结论是“用户尚未查看天气预报结果”，判为未完成。
- 这属于反思过严：模型给“搜索”追加了指令没有要求的“查看结果”。T1、T3、T4、T5 的反思都正确。
- 这个问题已作为缺陷 #10 修复。复测时 T2 3/3 通过，15 次反思全部判“完成”，与检查器 15/15 一致。
- 复测中，改判完成的规则把关一次都没有触发。改进后的提示词已经让 qwen3:8b 自己给出了正确结论，例如“任务目标是‘在浏览器中搜索天气预报’，所有相关子任务均已成功执行”。规则把关保留下来，作为兜底。
- 缺陷 #11 的动作补齐在复测的 3 次 T2 中都触发了：清空误填的 target_text「天气预报」或「天气预报 -搜索」，并补上回车。

**Act 阶段**
- 15 次运行共有 51 个 LLM 决策步，第一次输出就合格的有 39 步（76%）。
- 其余 12 步被校验器拦下，带着原因重试后全部改对，最终 51/51 动作正确。
- 修复后的复测中，51 步里第一次就合格的有 40 步（78%），和修复前基本持平。这两项修复针对的是反思和输入动作的细节，并不改变模型第一次输出的质量。
- 被拦下的典型错误：
  - 子任务是“打开浏览器 / 打开模拟聊天”，模型却去点击屏幕上无关的文字，例如“中国天气网”“https://www.bing.com”“天气预报”；
  - 应该用 open_app 时，输出了 scroll 或 done；
  - “直接输入并回车”的子任务输出成了 click。
- 这说明在 8B 模型上，**校验 + 带原因重试**这一层是必需的；没有这一层，第一次输出就会有约四分之一的步骤出错。

**耗时**
- 纯 LLM 决策下，每步多一次 qwen3:8b 调用和一次全屏 OCR。
- 用时是 hybrid + qwen3:8b 的 2.4～7 倍：T5 从 4.1 秒到 28.7 秒，T4 从 36.1 秒到 85.3 秒。

**结论**：
- 修复后，三种模式的成功率都是 15/15。
- 基础任务的步骤是确定的，用规则执行又快又稳；LLM 适合留给模板覆盖不到的开放指令。
- 纯 LLM 决策的可靠性依赖“校验 + 带原因重试 + 动作补齐”这一层。第5周优化模型时，以首次合格率（76%～78%）和耗时（hybrid 的 2.4～7 倍）为基线。
