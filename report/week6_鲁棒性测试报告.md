# 第6周 鲁棒性测试报告：GUI 智能体 v1.0 vs v2.0

项目：基于多模态大模型的桌面GUI智能体开发与优化
第6周交付物 | 2026年11月24日

## 一、结论

| 指标 | v1.0（第4周） | v2.0（第6周） |
|---|---|---|
| 故障注入评测成功率（14 种故障，1260 次运行中各 630 次） | 405/630 = **64%** | 589/630 = **93%** |
| 其中 12 种“可恢复”故障 | 355/540 = 66% | 539/540 = **99.8%** |
| 受故障影响的聊天类任务（T4/C2/C3/C4，可恢复故障） | 40/180 = 22% | 179/180 = 99.4% |
| **误报成功**（Agent 说完成了，检查器判定没完成） | **20 次** | **0 次** |
| 把文字输入到错误窗口 | 40 次 | 0 次 |
| 重复启动同一个程序 | 20 次 | 0 次 |
| Ollama 连不上时（llm_down） | 0/45 | 45/45（熔断后自动改用规则模式） |
| 真实 EasyOCR 每次感知耗时（Xvfb 1920×1080，聊天窗口 900×600） | 5.20 秒（全屏） | 1.52 秒（只识别前台窗口），画面不变时 0.04 秒（缓存） |
| 第6周新增测试用例 | — | **384 个**（云端可运行的 376 个全部通过，8 个 Windows 真机用例待本机运行） |
| 全量回归 | — | 1662 个：1570 通过、92 跳过（真机/GPU/LLM）、**0 失败** |

两种设计上就无法恢复的故障（联系人 15 秒后才出现、“发送”按钮只有图标没有文字），v2 和 v1 一样失败，但 v2 **如实报告失败原因**，没有误报成功、没有乱点。这一点是本周的设计目标之一：鲁棒性不仅是“多成功”，也是“失败时不撒谎、不造成副作用”。

## 二、测试对象

### 2.1 v2.0 新增的鲁棒性机制

| 机制 | 模块 | 作用 |
|---|---|---|
| 复杂任务分解 | `agent/decomposer.py` | 多步指令 → 目标(Goal) → 子任务；每个目标带“完成检查”（后置条件）和“能否整体重做”标记 |
| 错误分类 | `agent/recovery.py: classify_error` | 12 类：目标找不到、没有效果、焦点丢失、弹窗、截图/识别失败、程序窗口没出现、LLM 服务、完成检查不通过、非法动作、执行异常、用户中止、未知 |
| 按类重试 | `RetryPolicy` | 每类单独的最大次数，指数退避 0.5/1/2/4 秒，总次数上限 6 |
| 恢复动作 | `recovery_actions` + `WindowGuard` | 关闭“本次运行之后新出现的”通知类弹窗（不动用户原有窗口）、重新激活目标程序、等待迟到窗口（避免重复启动）、第 3 次找不到目标时放大截图再识别 |
| 熔断降级 | `CircuitBreaker` | LLM 连续失败 2 次 → 120 秒内改用规则决策 |
| 动作效果校验 | `agent/verifier.py: EffectVerifier` | 点击/双击/输入/拖拽前后截图对比（320×180 RGB、每通道阈值 12），画面没变化 = 动作没生效 → 重试 |
| 目标后置条件 | `Postcondition` | 窗口存在/不存在/在前台、屏幕上有/没有某段文字（容忍 OCR 错 1 个字符）、文件包含内容 |
| 目标整体重做 | `GUIAgentV2.run_goal` | 子任务都“成功”但完成检查不通过 → 可重放的目标整体重做一次；发消息这类不可重放目标不重做（避免重复发送） |

### 3.3 典型失败分析

| 现象 | v1 为什么失败 | v2 怎么处理 |
|---|---|---|
| **lost_click：v1 误报成功 20 次** | 点击“发送”被吞掉，v1 只看“点击动作执行了没报错”就算成功，最后反思也只看文字列表 | 点击后对比前后截图，画面没变 → 判定 no_effect 重试；目标结束时检查“屏幕上出现 张三：…” |
| 弹窗/抢焦点：v1 把文字输入到别的窗口（40 次） | 不知道前台窗口变了，照常点击和输入 | 每个子任务前检查前台窗口；关闭本次运行后新出现的通知弹窗、重新激活目标程序 |
| slow_window：v1 重复启动程序（20 次） | 等 2 秒没看到窗口就再启动一次 | 先等迟到窗口（最多 8 秒），确认没有才重新启动 |
| slow_load | 固定 2 次重试、间隔 0.5 秒，总共只等约 1 秒 | target_not_found 类最多尝试 4 次，按 0.5/1/2 秒退避，并在重试前关弹窗、重新激活程序 |
| screenshot_fail | 截图异常直接让整步失败 | 归类为 screenshot，等待 0.5 秒重拍 |
| llm_down | 每步都要调 LLM，全部失败 | 熔断器：连续 2 次服务错误 → 改用规则决策，任务照常完成 |
| ocr_typo（v2 唯一一次失败，C2 种子 4） | — | “李四”被识别成 2 个字都错的词，文字匹配无法恢复；重试 3 次后如实报告“屏幕上没有找到 李四”。这是 OCR 能力的边界，不属于重试能解决的问题 |
| slow_load_long / ocr_blind | 同 v2 | 重试 3 次（退避共 3.5 秒）后停止，报告“屏幕上没有找到 [张三]”/“[发送]”，**没有误报、没有乱点**。前者需要更长的等待预算（`--budget`），后者需要第5周的视觉模型（`--act vlm`）定位图标按钮 |

## 七、已知局限

1. **OCR 错两个字以上无法恢复**（ocr_typo 的 1 次失败）。文字匹配只容忍 1 个字符差异，再放宽会把“张三”和“张王”混淆。
2. **纯图标按钮**（ocr_blind）仍需要第5周的视觉模型；v2 目前只用 OCR + 控件检测，控件检测能找到按钮框，但不知道哪个是“发送”。
3. **等待上限**：target_not_found 最多尝试 4 次、退避共 3.5 秒，超过的慢加载（slow_load_long）会失败，可以用 `--budget` 加大总预算，但重试次数上限没有开放到命令行。
4. 故障注入评测是模拟桌面，真实 Windows 下的弹窗标题、焦点行为可能不同；Xvfb 没有窗口管理器，焦点行为也比 Windows 简单。需要本机跑 C5/C6 确认（第八节）。
5. 后置条件中的“屏幕上出现文字”依赖 OCR，每个目标结束时多一次识别；有缓存时开销很小，没有缓存时每个目标多 1~5 秒。
